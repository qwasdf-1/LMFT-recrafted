# Minecraft 26.3 tag-recovery hook investigation

Status: **source-reviewed design; not yet compiled or game-tested**  
Baseline: LMFT `1.21.x` at `94c2ed10`; target Minecraft 26.3.  
Scope: determine the safest 26.3 recovery and tag-identity injection points without rewriting vanilla tag resolution.

## Evidence

- Decompiled Minecraft 26.3 `net.minecraft.tags.TagLoader`:
  https://mc-packet-reference.netlify.app/26.x/source/net/minecraft/tags/tagloader/
- NeoForge 26.3 tag-loader patch:
  https://github.com/neoforged/NeoForge/blob/26.3.x/patches/net/minecraft/tags/TagLoader.java.patch
- Existing LMFT recovery mixin:
  `common/src/main/java/io/wispforest/lmft/mixin/TagGroupLoaderMixin.java`
- Forgiving Tags 26.3 Fabric/NeoForge JARs inspected independently; their shared
  `TagLoaderMixin` uses `@WrapOperation` on `List.isEmpty()` and
  `@Inject` on compiler-generated `lambda$build$1(...)`.

## Verified 26.3 control flow

`TagLoader.load(ResourceManager)` merges tag entries from resource packs.
`TagLoader.build(Map)` constructs a `DependencySorter<Identifier, SortingEntry>`
and calls `orderByDependencies(BiConsumer)` to process each tag in order.
The callback receives the tag `Identifier` and the corresponding sorting entry.

`TagLoader.tryBuildTag(TagEntry.Lookup, List<EntryWithSource>)`:
1. Adds resolved entries to an insertion-ordered `SequencedSet`.
2. Adds unresolved required entries to `missingElements: ArrayList`.
3. Returns either the valid entries or the unresolved entries:

```java
return missingElements.isEmpty()
    ? Either.right(List.copyOf(values))
    : Either.left(missingElements);
```

**Therefore the existing recovery seam is still appropriate:** before
`missingElements.isEmpty()`, record unresolved entries, clear that list,
and permit vanilla to return `Either.right` containing the already-resolved
entries. It also accepts an empty tag when all entries are unresolved, as
LMFT has historically done.

NeoForge 26.3 modifies the entry-processing loop to support tag removals,
but retains the same `missingElements` list and branch. Do not replace its
loop or override `TagEntry.build`: those would interfere with removal
semantics.

## Preferred hooks for 26.3 (proposed)

### 1. Recovery: retain `@WrapOperation` on the `isEmpty()` invocation

```java
@WrapOperation(
    method = "tryBuildTag(Lnet/minecraft/tags/TagEntry$Lookup;Ljava/util/List;)Lcom/mojang/datafixers/util/Either;",
    at = @At(value = "INVOKE", target = "Ljava/util/List;isEmpty()Z"),
    require = 1
)
private boolean lmft$recover(
        List<?> missing, Operation<Boolean> original) {
    LMFTCommon.handleAndLogInvalidEntries(missing);
    return original.call(missing);
}
```

A `@WrapOperation` is preferable to a redirect because it composes with
other wrappers and preserves the original call. The handler above assumes
the core implementation logs and empties `missing` without replacing it.

### 2. Tag identity: wrap the `orderByDependencies` callback in `build`

Instead of targeting the unstable synthetic `lambda$build$1`, intercept
the argument passed to the explicitly named
`DependencySorter.orderByDependencies(BiConsumer)`. Conceptual Mixin:

```java
@ModifyArg(
    method = "build(Ljava/util/Map;)Ljava/util/Map;",
    at = @At(
        value = "INVOKE",
        target = "Lnet/minecraft/util/DependencySorter;orderByDependencies(Ljava/util/function/BiConsumer;)V"
    ),
    index = 0,
    require = 1
)
private BiConsumer<Identifier, Object> lmft$withTagContext(
        BiConsumer<Identifier, Object> original) {
    return (id, entry) -> {
        LMFTCommon.setTagId(id);
        try {
            original.accept(id, entry);
        } finally {
            LMFTCommon.clearTagId();
        }
    };
}
```

This is a **proposal to compile and validate**, not a proven mixin:
method descriptors and local ordering must be checked against the
resolved 26.3 development classes for each loader. The mixin should
never need to reference private `TagLoader.SortingEntry` as a Java
type: `BiConsumer` is the relevant erased argument.

Benefits:
- No dependency on a generated lambda method name or argument index.
- Tag IDs are associated with the *whole* callback, not a single
  expression inside it.
- `finally` reliably clears per-thread context, including successful
  tag loads and exceptions.
- No extra work on server ticks; the wrapper runs while building tags.

Trade-off: this couples to the stable-looking but internal
`DependencySorter.orderByDependencies(BiConsumer)` call. It should
remain `require = 1` so a Minecraft change cannot silently disable
tag-ID logging. If the callback becomes asynchronous, this scope would
need redesign; current 26.3 code uses it synchronously.

### Rejected alternatives

- Patch `Either.left` after `tryBuildTag`: valid values have already been
  discarded from the return value.
- Change individual `TagEntry.build` lookups: potentially alters required/
  optional semantics and conflicts with NeoForge tag removals.
- Inject at `lambda$build$1` as Forgiving Tags does: works on 26.3, but
  depends on a synthetic ordinal that may change between versions.
- Use `require = 0` across many aliases without a coverage test: risks
  silently loading the mod while no recovery hook is active.

## Verification gates before shipping

1. **Compile** with Minecraft 26.3 Fabric Loom and NeoForge ModDevGradle.
   Confirm both `@ModifyArg` and `@WrapOperation` resolve to exactly one
   intended invocation. Check logs; fail fast if either injector cannot apply.
2. **Fabric and NeoForge dedicated servers**: a data pack adds one valid
   element plus a nonexistent required element to a vanilla block tag.
   Verify the valid element remains and the missing entry is logged with
   its *correct tag ID*.
3. Two broken tags in one reload: correct individual IDs, no context bleed.
4. A valid tag after a broken tag: no erroneous skipped-entry warning and
   no retained thread-local identifier.
5. A missing **optional** element: no recovery warning.
6. Missing required **tag reference**: log and keep valid elements.
7. NeoForge removal entry: ensure LMFT doesn't interfere with valid
   removals or treat optional missing removals as failures.
8. Repeat `/reload` and player joins; verify state reset and notification
   permissions, including zero-operator users.
9. Inspect Mixin debug exports and run with other common tag-related mods.
10. Only after passing 26.3, check 26.1, 26.2, and 1.21.11 separately;
    these are **not yet verified** to have identical bytecode targets.

## Branch/build separation

Keep the existing 1.21.11 Architectury setup usable.
Introduce version-specific 26.3 build modules/source sets before adding
active 26.3 mixins; do not mix 26.3 identifiers into the current
1.21.11 Java compilation target. Preserve common recovery behavior and
configuration file `lmft.json` where practical. Avoid treating a
single universal JAR as a release requirement until compatibility is
demonstrated by the runtime matrix.
