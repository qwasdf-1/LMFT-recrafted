# LMFT-recrafted: Minecraft 26.x JAR compatibility audit

Date: 2026-11-23. Status: binary audit complete; cross-loading a single JAR
across Minecraft versions **not yet tested**.

## Evidence

Compiled artifacts were obtained from successful GitHub Actions runs:

- 26.1, 26.1.1, 26.1.2, 26.2 (Fabric and NeoForge):
  https://github.com/qwasdf-1/LMFT-recrafted/actions/runs/45257979268
- 26.3 Fabric and NeoForge:
  https://github.com/qwasdf-1/LMFT-recrafted/actions/runs/45255530969
- Actual 26.3 server membership and reload tests:
  https://github.com/qwasdf-1/LMFT-recrafted/actions/runs/45260660306

For each loader and version, I unpacked the Actions artifact ZIP, selected the
non-sources mod JAR, hashed its compiled `.class` entries, and compared all
class names and byte contents.

| Loader | Versions | Byte-for-byte class-file result |
|---|---|---|
| Fabric | 26.1, 26.1.1, 26.1.2, 26.2, 26.3 | All 8 compiled classes identical |
| NeoForge | 26.1 and 26.1.1 | Same 8 classes within this group |
| NeoForge | 26.1.2, 26.2, 26.3 | Same 8 classes within this group |
| NeoForge | Compare the two groups | Exactly one changed class: `io/wispforest/lmft/mixin/TagLoaderMixin.class` |

Differences outside the class files:

- Fabric: `fabric.mod.json` and `META-INF/MANIFEST.MF` differ by version.
- NeoForge: `META-INF/neoforge.mods.toml` differs by version.

### The NeoForge annotation difference

Comparing the 26.1 and 26.2 `TagLoaderMixin.class` files using `javap -v`
shows that `@ModifyArg(at=...)` is serialized with a **single** `@At`
annotation on 26.1 but an **array of** `@At` annotations on 26.2.

The target method descriptor, hook target, Java method bodies and other
annotations were unchanged. This appears to reflect a Mixin annotation API
difference between toolchains, rather than a Minecraft tag-loading algorithm
change. We should not assume a class file compiled with one representation
will be interpreted correctly by the other runtime.

### Conclusions

1. **Fabric is an excellent candidate** for a single compiled JAR across the
   26.x family. Its class bytecode is already identical across all five
   independently built versions. A candidate still needs wide version
   metadata and actual runtime cross-load tests on all five releases.
2. **NeoForge is a plausible candidate but has an additional obstacle.**
   The `@ModifyArg` annotation serialization differs across the 26.1/26.1.1
   and 26.1.2+ lines. Test cross-loading explicitly or replace this single
   injector with a stable annotation form and rerun the runtime matrix.
3. Until cross-loading is proven, distribute independently compiled,
   version-pinned JARs. One shared Java source tree is already in place.
4. None of these differences suggest a meaningful server-tick performance
   impact from unused class files. The issue is class loading/Mixin startup
   correctness and loader metadata, not steady-state CPU cost.

## Proposed universal-JAR acceptance gate

- Build the candidate *once* per loader, including permissive but bounded
  Minecraft/loader dependency ranges.
- Install exactly that produced artifact (not a recompiled version) on every
  supported Minecraft release in an isolated dedicated server.
- Run the same recovery, tag-membership, multi-reload and NeoForge removal
  assertions as the version-pinned builds.
- Verify mixin application and errors in each server log.
- Test joining clients, operator-only notifications, and clean reloads
  before publishing universal compatibility.

Do not change public dependency ranges or advertise single-JAR compatibility
solely on the basis of classfile hashes.
